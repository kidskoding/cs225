Each member of a class in C++ has a specific {\bfseries{access level}} that determines how that member can be accessed

A member can be one of three types\+: {\bfseries{public}}, {\bfseries{private}}, or {\bfseries{protected}}
\begin{DoxyItemize}
\item {\ttfamily private} -\/ Members declared as private can only be accessed from {\bfseries{within the same class}}
\item {\ttfamily protected} -\/ Members declared as protected can only be accessed by derived classes (subclasses)
\item {\ttfamily public} -\/ Members declared as public can be accessed {\bfseries{anywhere}} (inside the class, from other classes, or even outside the class)
\end{DoxyItemize}

\hypertarget{md_programming_autotoc_md11}{}\doxysubsubsubsection{\texorpdfstring{Classes vs Structs}{Classes vs Structs}}\label{md_programming_autotoc_md11}
\begin{quote}
Members of a {\ttfamily struct} are {\ttfamily public} by default Members of a {\ttfamily class} are {\ttfamily private} by default \end{quote}


That is the simple difference between a {\ttfamily class} and a {\ttfamily struct}

The keywords {\ttfamily public} {\ttfamily protected} and {\ttfamily private} can explicitly define access levels of functions and variables for both a struct or class.

However, it is {\bfseries{best practice}} for a struct to not use any access specifiers (all members will anyway default to {\ttfamily public}) and for a class to make member variables {\ttfamily private} (or {\ttfamily protected}) and methods {\ttfamily public}

A {\ttfamily struct} is typically used when
\begin{DoxyItemize}
\item There is a simple collection of data that doesn\textquotesingle{}t benefit from restricting access
\item Aggregate initialization is sufficient (no need for object)
\item Structs should be aggregates by convention, where direct initialization of members are allowed through an initializer list {\ttfamily \{ \}} and there are no {\bfseries{constructors}}, no {\bfseries{private/protected access members}}, no {\bfseries{virtual functions}}, and no {\bfseries{base classes}}
\end{DoxyItemize}

Otherwise, just use classes\hypertarget{md_programming_autotoc_md12}{}\doxysubsubsubsection{\texorpdfstring{Member Functions}{Member Functions}}\label{md_programming_autotoc_md12}
{\bfseries{Member functions}} are functions that belong to a class type. This means that they can be called on an instance of that class type (e.\+g. {\ttfamily e.\+get\+Data()} , where {\ttfamily get\+Data()} is a member function of object type {\ttfamily e})
\begin{DoxyItemize}
\item This means they are declared in the class definition!
\end{DoxyItemize}

\begin{quote}
C\# and Java refer to these as methods, since they are object oriented languages at the core. They aren\textquotesingle{}t referred to as methods in C++, but the idea still remains the same \end{quote}


Functions that don\textquotesingle{}t belong to a class are {\bfseries{non-\/member functions}} or simply {\bfseries{free functions}}.

With free functions, the object must be explicitly passed into the function, while with member functions, the object is implicitly passed and accessed through that object with the dot operator ({\ttfamily .})

{\bfseries{Dynamic Memory Allocation}} assigns memory space during a program\textquotesingle{}s execution rather than compile time. This memory that the program uses is generally divided into the {\bfseries{stack}} and the {\bfseries{heap}}. \hypertarget{md_programming_autotoc_md17}{}\doxysubsubsection{\texorpdfstring{{\ttfamily new} and {\ttfamily delete}}{{\ttfamily new} and {\ttfamily delete}}}\label{md_programming_autotoc_md17}
C++ supports static and automatic memory allocation. {\bfseries{Automatic allocation}} creates variables that live only while the function runs (on the stack), while {\bfseries{static allocation}} creates variables that stay alive for the whole program (in static memory). The period in which a variable stays alive is known as its {\bfseries{lifetime}}

Lifetime based on allocation type
\begin{DoxyItemize}
\item {\bfseries{Automatic objects}}\+: lifetime ends when they go {\bfseries{out of scope}} (e.\+g., when a function/block ends)
\item {\bfseries{Static objects}}\+: lifetime ends when the {\bfseries{program terminates}}
\end{DoxyItemize}

With these two methods, the size of the variable/array must be known at compile time, and memory allocation and deallocation happen automatically (when a variable is instantiated/destroyed)

However, there may be situations where declaring a fixed size memory may lead to a waste of unused memory or there are more allocated objects of memory than what was assigned.

To fix this problem, memory can be manually managed dynamically, which is known as {\bfseries{dynamic memory allocation}}. This is done using two keywords {\ttfamily new} and {\ttfamily delete}

{\ttfamily new} -\/ {\bfseries{Dynamically allocate memory at runtime on the heap for an object/array}}. Also calls the {\bfseries{constructor}} to initialize the object and returns a typed pointer to the allocated memory
\begin{DoxyItemize}
\item This is very similar to {\ttfamily malloc} in C (They actually do the same thing!). However, {\ttfamily malloc} is by default a void pointer ({\ttfamily void\texorpdfstring{$\ast$}{*}}) and needs to be casted to the appropriate pointer type. Therefore in modern C++, {\ttfamily new} is highly recommended.
\end{DoxyItemize}

{\ttfamily delete} -\/ {\bfseries{Frees memory allocated by}} {\ttfamily new}. Also calls the {\bfseries{destructor}} to clean up the object. Must match the type of allocation ({\ttfamily delete} for single objects and {\ttfamily delete\mbox{[}\mbox{]}} for arrays)
\begin{DoxyItemize}
\item Ensure that the pointer points to a valid object (has a valid address of memory!). Otherwise, unpredictable behavior can happen!
\item Similar to {\ttfamily free} in C, but since there are no destructors, {\ttfamily free} wont call the destructor if there is any
\item {\bfseries{Ends the lifetime of the object the pointer points to!}}
\end{DoxyItemize}

Note that when you use {\ttfamily delete}, even though the object is freed from memory, its pointer now points to {\bfseries{invalid memory}}. This is a {\bfseries{dangling pointer}}. Therefore, it is best practice to set the pointer to {\ttfamily nullptr} (null) after using {\ttfamily delete}, as suggested in the code snippet below, which avoids the dangling pointer.


\begin{DoxyCode}{0}
\DoxyCodeLine{int*\ xPtr\ =\ new\ int(5);}
\DoxyCodeLine{delete\ xPtr;}
\DoxyCodeLine{xPtr\ =\ nullptr;}

\end{DoxyCode}


While static and automatic memory management free variables from memory its lifetime ends or out of scope respectively, memory must be explicitly freed with {\ttfamily delete} when dynamically allocated.

\begin{quote}
In other words, when creating memory calls with {\ttfamily new} they {\bfseries{must}} be freed with {\ttfamily delete}. \end{quote}


Otherwise, a {\bfseries{memory leak}} happens. {\bfseries{Memory leaks}} occur when a program allocates memory via {\ttfamily new}, but never frees it via {\ttfamily delete}. {\bfseries{Resource Acquisition Is Initialization}}, or RAII, is a C++ programming design pattern that explains how to manage resources safely in a class through a constructor and a destructor. RAII is used heavily in the C++ STL (standard template library) for efficient resource management in objects.

\begin{quote}
\mbox{[}!\+RAII\mbox{]} You acquire a resource (memory, file, lock, etc.) via an object\textquotesingle{}s {\bfseries{constructor}} and you automatically release that resource via the object\textquotesingle{}s {\bfseries{destructor}} \end{quote}


In other words, an object {\bfseries{acquires}} a resource in its {\bfseries{constructor}} and {\bfseries{releases}} it in its {\bfseries{destructor}}

These resources can include anything the class owns or manages
\begin{DoxyItemize}
\item A file handle
\item A pointer to dynamic memory
\item A mutex lock
\item A network connection
\end{DoxyItemize}

RAII is a basic technique that explains best practices towards writing a class by {\bfseries{tying an object\textquotesingle{}s resources to its lifetime}}
\begin{DoxyItemize}
\item An object acquires a resource in its constructor, and releases it via its destructor when its lifetime ends
\end{DoxyItemize}\hypertarget{md_programming_autotoc_md20}{}\doxysubsubsection{\texorpdfstring{Heap}{Heap}}\label{md_programming_autotoc_md20}
The heap, also known as the {\bfseries{free store}}, {\bfseries{tracks memory used for dynamic memory allocation}}

Recall that {\ttfamily new} allocates memory and returns a pointer that points to that allocated memory. In contrast, {\ttfamily delete} frees the allocated memory towards the operating system to decide what to do with that memory next.

This dynamic memory allocation behavior is all managed via the heap. This means that {\ttfamily new} will allocate memory onto the heap and {\ttfamily delete} will return the allocated memory from the heap, where the operating system can decide what to do with this memory later.

{\bfseries{Heap Advantages and Disadvantages}}
\begin{DoxyItemize}
\item Allocating memory on the heap is slow
\item Allocated memory stays allocated until the programmer deallocates the memory themselves or the application ends (OS cleans it up)
\begin{DoxyItemize}
\item Even though an OS will clean up dynamically allocated memory at the end of the program, {\bfseries{memory leaks}} are still bad practice and you should always {\ttfamily delete} dynamically allocated memory
\begin{DoxyItemize}
\item This is a problem for bigger programs that handle lots of data, where they can possibly slow down, crash, or cause system instability
\end{DoxyItemize}
\end{DoxyItemize}
\item Dynamically allocated memory must be accessed through a pointer. Therefore, dereferencing a pointer is slower than accessing a variable directly
\item Because the heap is a big pool of memory, large arrays, structures, or classes can be allocated here
\end{DoxyItemize}\hypertarget{md_programming_autotoc_md21}{}\doxysubsubsection{\texorpdfstring{Stack}{Stack}}\label{md_programming_autotoc_md21}
The {\bfseries{stack}}, formally referred to as the {\bfseries{call stack}}, keeps track of all active functions (ones that have been called and not terminated) from the start of the program to the current point of execution. It also handles allocation of all function parameters and local variables

It stores
\begin{DoxyItemize}
\item {\bfseries{Local Variables}} -\/ function parameters and variables declared inside functions
\item {\bfseries{Function call information}} -\/ where to return after a function finishes
\end{DoxyItemize}

When a function is called, a stack frame is created on top of the call stack that holds the function\textquotesingle{}s local data. When the function ends, its stack frame is removed, and the memory is automatically reclaimed

{\bfseries{Key Details}}
\begin{DoxyItemize}
\item The stack is {\bfseries{fast}} because elements are accessed in a {\bfseries{LIFO}} (Last In First Out) format. This means that both removal and insertion is \$\+O(1)\$
\item Variables in the stack have automatic storage duration and only exist when the function is running
\item Limited size (few MBs), so you can run out of stack space if you create too many local variables or deep recursion
\end{DoxyItemize}

All in all, the {\bfseries{stack}} is memory for {\bfseries{local variables}} that are automatically managed and exist only when a function is {\bfseries{running}}. The {\bfseries{heap}} is slower memory for {\bfseries{dynamically allocated variables}} ({\ttfamily new}) that must be managed {\bfseries{manually}} with {\ttfamily delete}


\begin{DoxyItemize}
\item {\bfseries{Stack data}}\+: local variables inside functions, function parameters, pointer variables themselves (not what they point to)
\begin{DoxyItemize}
\item Used for short-\/lived, simple variables
\end{DoxyItemize}
\item {\bfseries{Heap data}}\+: Any variable dynamically allocated via {\ttfamily new} or {\ttfamily malloc}
\begin{DoxyItemize}
\item Use when a variable is needed to outlive the function or for large or dynamically-\/sized data
\end{DoxyItemize}

{\bfseries{Shallow}} and {\bfseries{deep}} copies define how objects are copied!

A {\bfseries{shallow copy}} occurs where an object\textquotesingle{}s {\bfseries{pointers}} are copied, but {\bfseries{not}} {\bfseries{the data they point to}}
\begin{DoxyItemize}
\item Both the object and the copied object share the same underlying data, which means that changing one pointer affects both objects
\item If one object deletes or modifies the pointer, the other may be left with invalid data, causing crashes and segmentation faults resulting in undefined behavior or unexpected data, which may contain varied data than what was ideal
\end{DoxyItemize}

A {\bfseries{deep copy}} is a completely independent copy of all data, including an object\textquotesingle{}s pointers and the memory they point to
\begin{DoxyItemize}
